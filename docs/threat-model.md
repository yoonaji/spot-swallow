# 위협 모델과 신뢰 경계 (2026-11-29)

전제는 하나다. **스팟 워커는 언제 꺼질지 모르고, 믿을 수도 없는 서버다.** 회수되면 디스크와 메모리가 남의 손에 갈 수 있고,
털리면 그 안의 계정으로 할 수 있는 일은 다 할 수 있다고 본다. 그래서 질문은 "워커를 어떻게 지키나"가 아니라
**"워커가 털려도 돈이 틀리지 않게 하려면 무엇을 맡기지 말아야 하나"** 이다.

이 문서의 "됨"은 모두 시험으로 확인한 것이고, 근거 파일을 함께 적었다.

## 1. 신뢰 경계

```
 ┌──────────────── 안정 영역 (온디맨드, 신뢰) ────────────────┐        ┌──── 스팟 영역 (신뢰 안 함) ────┐
 │  settlement-api ── outbox 발행 ──► RabbitMQ ───────────────┼──전달──►│  settlement-worker × N        │
 │       │  대사·감사 검사                                     │        │   계산 → 결과 INSERT → Ack     │
 │       ▼                                                     │        │                                │
 │  PostgreSQL ◄───────────────────────────────────────────────┼─INSERT─┤  계정: swallow_worker_app      │
 │   결과 · 이력 · 감사 체인(트리거)                           │        │  (결과·이력 추가만)            │
 │       │                                                     │        └────────────────────────────────┘
 │       ▼ 1분마다 끝 해시                                      │
 │  앵커 저장소 (DB 와 다른 곳, 추가만)                         │
 └─────────────────────────────────────────────────────────────┘
```

| 경계 | 넘어가는 것 | 지키는 것 |
|---|---|---|
| 큐 → 워커 | 작업 ID 하나 (금액 없음) | 워커는 금액을 받지 않고 DB 의 불변 입력 거래로 계산한다 |
| 워커 → DB | 결과 한 줄 INSERT, 완료 표시, 이력 한 줄 | 워커 계정 권한이 추가만 허용. 결과 PK 로 한 번만 확정 |
| DB → 앵커 저장소 | 감사 체인 끝 (seq, hash) | DB 관리자와 다른 권한의 저장소에 추가만 |
| EC2 부팅 → 비밀 | DB 계정 | 이미지에 비밀 없음. Vault 가 1시간짜리 계정을 1회용 토큰으로 발급 (EC2 측정 구성) |

## 2. 공격자와 대응

| # | 공격자 / 사건 | 하려는 것 | 막는 것 (차단) | 잡는 것 (탐지) | 근거 |
|---|---|---|---|---|---|
| T1 | 회수·장애로 워커가 아무 때나 죽음 | (악의 없음) 유실·중복 | 커밋 후 Ack, 결과 PK, Outbox, DLQ | 대사(유실·중복·금액) | 강제 종료 1,449회 유실·중복 0 (`week3-kill-1000.md`), 장애 지점 8종 × 3회 작업 9,600건 (`week3-fault-matrix.md`) |
| T2 | 털린 스팟 워커 | 확정된 결과·이력 변경/삭제, 입력 거래 변경 | 워커 계정은 결과·이력 INSERT 만, 거래는 읽기만 | 대사 | `security_drill.py` A: 11개 시도 모두 거부 |
| T3 | 털린 스팟 워커 | 감사 기록 위조·끄기, 권한 올리기 | 감사 표·기록 함수 접근 불가, 트리거 끄기는 소유자만 | | 같은 시험 A |
| T4 | 털린 스팟 워커 | 틀린 금액을 처음부터 INSERT | (막지 못함: 워커가 계산하는 구조) | 대사가 입력 거래로 다시 계산해 비교 | GameDay 1회차 감지 10초 (`gameday/report-1.md`) |
| T5 | 회수된 인스턴스의 디스크·메모리 | DB 계정 탈취 | 이미지에 비밀 없음, 계정 1시간 만료 (EC2 구성) | | `tready-ec2.md` 보안 부트스트랩 |
| T6 | DB 관리자 계정으로 결과 직접 변경 | 금액 조작 | (막지 않음: 정정이 필요할 수 있음) | 감사 체인에 계정·주소가 남고, 금액이 틀리면 대사 | 시험 B |
| T7 | DB 관리자가 감사 트리거를 끄고 변경 | 흔적 없이 변경 | | 결과가 마지막 감사 기록과 달라짐 (`untracked`) | 시험 C: 금액이 아닌 값이라 금액 대사로는 0 이었지만 체인이 잡음 |
| T8 | DB 관리자가 감사 기록까지 고침 | 흔적 지우기 | 감사 표는 소유자도 UPDATE·DELETE·TRUNCATE 불가 | 해시 체인 끊김 (`brokenLinks`) | 시험 D |
| T9 | DB 관리자가 체인 전체를 다시 계산해 덮음 | 완전한 은폐 | | DB 밖 앵커와 다름 (`anchorMismatch`) | 시험 E: DB 안 검사는 모두 0 으로 속았지만 앵커가 잡음 |

탐지는 모두 대사 한 곳으로 모이고, Grafana "대사 불일치 발생" 알림 하나로 울린다. 대응 절차는 `runbook.md`.

## 3. 우선순위: 왜 이 순서로 했나

1. **탐지 (대사)** 를 먼저 만들었다. 무엇이 어떻게 틀려도 "돈이 틀렸다"는 사실은 입력 거래로 다시 계산하면 알 수 있다. 막는 장치가 하나도 없어도 이것만 있으면 사고가 조용히 지나가지 않는다.
2. **차단 (최소 권한)** 은 GameDay 에서 "대사로 잡긴 했지만 애초에 UPDATE 가 됐다"는 것을 보고 넣었다. 가장 자주 바뀌고 가장 믿을 수 없는 쪽(스팟 워커)의 권한부터 줄였다.
3. **추적 (감사 체인과 앵커)** 은 "잡았지만 누가 했는지 모른다"를 메운다. 관리자는 막을 수 없으니(정정이 필요하므로) 남기고 드러나게 한다.

## 4. 보안 비용

- Vault 동적 시크릿 부트스트랩: p50 92ms, 복구 시간(Tready)의 약 1% (EC2 20회). 복구 시간이 늘어 여유 서버를 더 둬야 할 만큼의 비용이 아니었다.
- 워커 최소 권한: 처리 경로 변화 없음. 처음에는 권한을 너무 좁혀 작업 40건이 전부 DLQ 로 갔다(`ON CONFLICT` 검사가 결과 PK 칸 읽기를 요구). 그 한 칸만 더해 고쳤다.
- 감사 체인: 결과 확정마다 체인 기록을 한 번에 하나씩 한다(advisory lock). 위 실험에서 지연은 보이지 않았지만 처리량 영향은 따로 재지 않았다.

## 5. 아직 막지 못한 것 (알고 남겨 둔 것)

| 항목 | 위험 | 다음 단계 |
|---|---|---|
| 워커의 RabbitMQ 계정이 관리자 계정과 같다 | 털린 워커가 큐를 비우면 발행된 작업이 사라진다. 대사의 오래 대기한 작업(`stalePendingJobs`)으로 드러나지만 자동 복구는 없다 | 워커 전용 RabbitMQ 계정(작업 큐 소비만) |
| API·운영자는 DB 관리자 계정 하나를 쓴다 | API 가 털리면 DB 전체 권한 | API 계정 분리, 정정 전용 계정 |
| 관리·DLQ API 에 인증이 없다 | 같은 네트워크에서 합성 데이터 적재·DLQ 재처리 가능 | 토큰 또는 mTLS |
| 로컬 비밀번호가 고정 기본값 | 로컬 실험용. 운영 구성은 EC2 의 Vault 구성을 따라야 한다 | 로컬에도 Vault 적용 |
| 앵커가 로컬에서는 다른 Docker 볼륨의 파일 | 같은 호스트 관리자는 둘 다 고칠 수 있다. 마지막 앵커 이후(최대 1분) 변조는 못 잡는다 | 한 번 쓰면 지울 수 없는 외부 저장소, 주기 단축 |
| 워커가 처음부터 틀린 금액을 넣는 것(T4)은 막지 못한다 | 대사 주기만큼 틀린 값이 보인다 | 두 워커가 따로 계산해 일치할 때만 확정 (비용 2배) |
| 서비스 간 통신 암호화(mTLS)가 없다 | 같은 네트워크의 도청·위장 | 워크로드 신원(mTLS), 플랜의 "여유 시" 항목 |
| 인스턴스 교체 후 비밀·권한 동일, 종료 인스턴스 데이터 잔존 시험 | 확인 안 됨 | EC2 에서 두 시험 |
