# 설계 결정 기록

왜 이렇게 정했는지, 다른 선택지는 무엇이었는지, 무엇을 포기했는지를 적는다.
형식: 상황 → 결정 → 버린 대안 → 대가. 날짜는 결정한 날.

## D1. "정확히 한 번 전달" 대신 "최소 한 번 전달 + 멱등 반영" (2026-11-11)

- **상황**: 스팟 워커는 언제든 꺼진다. 메시지 큐와 DB 는 서로 다른 시스템이라, 한 번에 함께 커밋할 수 없다.
- **결정**: RabbitMQ 수동 Ack 로 "최소 한 번" 전달을 받고, 결과 테이블의 `job_id` PK 로 두 번째 반영을 막는다.
  Ack 는 DB 커밋이 끝난 뒤에 보낸다.
- **버린 대안**: 분산 트랜잭션(XA). RabbitMQ 가 지원하지 않고, 지원하더라도 코디네이터 자체가 장애 지점이 된다.
  Kafka 트랜잭션은 결과가 DB 에 있으므로 해결이 되지 않는다.
- **대가**: 같은 작업을 두 번 계산하는 비용. 1주차 측정에서 30% 강제 종료 시 51건을 다시 계산했지만 확정은 한 번이었다.

## D2. 작업 저장과 발행을 아웃박스로 묶음 (2026-11-11)

- **상황**: "DB 에는 작업이 있는데 큐에는 메시지가 없는" 상태가 생기면 그 정산은 영원히 처리되지 않는다.
- **결정**: 작업과 발행할 메시지를 같은 트랜잭션으로 `outbox` 에 쓰고, 별도 발행기가 Publisher Confirm 을 받은 뒤 완료 표시.
- **버린 대안**: API 에서 커밋 후 바로 발행. 커밋과 발행 사이에 죽으면 유실된다. CDC(Debezium)는 졸업프로젝트 규모에 비해 운영 부담이 크다.
- **대가**: 발행이 최대 200ms 늦어지고, 발행기가 죽으면 같은 메시지가 두 번 나갈 수 있다(D1 이 흡수).

## D3. 워커 자동 재시작을 끔 (2026-11-11)

- **상황**: docker 의 `restart: on-failure` 는 재시작 간격을 점점 늘려서, 장애 실험의 복구 시간이 실험자가 정한 값과 달라졌다.
- **결정**: 워커는 `restart: "no"`. 실험에서는 e2e.py 가, 3주차부터는 제어기가 Auto Scaling 그룹 역할을 맡는다.
- **대가**: 실험 스크립트 없이 compose 만 띄우면 죽은 워커가 돌아오지 않는다. README 에 적었다.

## D4. 온디맨드 대체를 알고리즘 안에 넣음 (2026-11-12, 11-16 구현)

- **상황**: 공개 trace 를 변환해 보니 한 영역의 다중 노드 풀은 f_w 의 q99 가 1.0 이었다. "전부 함께 회수"가 드물지 않다.
  K(n) = n 이면 스팟을 몇 대 띄워도 위험 구간 동안 남는 워커가 없다.
- **결정**: 알고리즘 1 의 탐색을 (스팟 n, 온디맨드 d) 두 변수로 넓히고, 식 (8)을 만족하는 조합 중 가장 싼 것을 고른다. d = 0 이면 원래 알고리즘과 같다.
- **버린 대안**: 스팟 상한까지 늘리고 안 되면 포기. 시뮬레이션에서 비용이 2.5배가 되고(ablation "온디맨드 제거") 스팟 용량이 없는 시간에 위반이 생겼다.
- **대가**: 온디맨드 가격 대비 스팟 가격이라는 입력이 하나 늘었다.

## D5. 식 (8)을 대기 시간 기반 조건으로 바꿈 (2026-11-16)

- **상황**: 중간보고서의 식 (8)은 "위험 구간 내내 기다린 작업이 남은 시간 안에 끝나야 한다"고 본다. 그래서 위험 구간(q95 Tready + Δ ≈ 330초)이
  완료시간 목표(300초)보다 길면 적체가 0 이어야 하고, 회수 1대만 있어도 위반으로 판단한다. 시뮬레이션에서 평상시에도
  고정 여유 +2 대보다 비쌌다(온디맨드 대비 0.57 vs 0.54, 위반은 둘 다 0).
- **결정**: 위험 구간 중 시각 τ 에 도착한 작업이 FIFO 로 실제 기다리는 시간을 계산하고, 그 최댓값 + 처리 시간이 목표 이하인지 본다 (식 8', `max_wait`).
- **결과**: 평상시 비용 33% 감소(0.57 → 0.38), 복구 지연 ×4 위반율 1.0% → 1.8%. 원형은 테스트에서 중간보고서 표 2 재현용으로 남겼다.
- **대가**: 계산이 조금 늘었다(τ 를 20등분). 위반율이 조금 오르므로 p 를 함께 조정해야 한다.

## D6. AWS Capacity Rebalancing 을 기준선으로 둠 (2026-11-16)

- **상황**: "AWS 가 이미 회수 경고와 자동 교체를 주는데 직접 계산하는 이유가 뭔가"라는 질문에 답해야 한다.
- **결정**: 여유 0 + 경고 즉시 교체를 하는 `aws-rebalance` 정책을 비교군에 넣고, 경고 시점(0초, 2분, 10분)을 바꿔 가며 비교한다.
  제안 기법과 함께 쓰는 `proposed+rebalance` 도 넣는다.
- **결과**: 복구가 경고 시간과 비슷하면 AWS 쪽이 낫고, 복구가 경고보다 훨씬 길면 제안 기법이 낫다. 함께 쓰는 것이 가장 낫다.
  "AWS 를 이긴다"가 아니라 "AWS 기능이 부족해지는 조건을 숫자로 찾았다"가 결론이다.
- **버린 대안**: Spot placement score 비교. 점수는 "어느 풀을 고를지"를 정하는 것이라 단일 풀 실험과 축이 다르다. 여러 풀 확장 때 다룬다.

## D7. 시뮬레이터를 직접 작성 (2026-11-16)

- **결정**: SimPy 없이 heapq 기반으로 300줄. 실험 하나(12시간, 작업 7.8만 건)가 1~3초다.
- **이유**: 회수 시 처리 중 작업이 큐 앞으로 돌아가는 동작, draining, 스팟 용량 없음 같은 세부를 실제 시스템과 똑같이 맞추려면
  사건 처리 순서를 직접 쥐는 편이 확인하기 쉽다. 의존성이 줄어 재현도 쉽다.
- **검증**: 실제 시스템과 같은 조건 비교에서 오차 8% 이내 ([week2-simulation.md](week2-simulation.md) 결과 4).

## D8. 제어 로직을 시뮬레이터와 실제 제어기가 공유 (2026-11-16)

- **결정**: `capacity/` 패키지는 시뮬레이터에 의존하지 않는다. 3주차 제어기는 Prometheus 에서 λ, Q, Tready 를 읽어 같은 `Controller.decide()` 를 부른다.
- **이유**: "시뮬레이션에서는 됐는데 실제로는 다르게 구현했다"는 차이를 없앤다.
