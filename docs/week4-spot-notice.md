# 회수 경고를 받으면 마무리하고 내려가기 (2026-11-25)

AWS 는 스팟 인스턴스를 회수하기 2분 전에 경고(중단 알림)를 준다. 지금까지 워커는 이 경고를 무시했고,
처리 중이던 작업은 회수 뒤 다른 워커가 처음부터 다시 계산했다(정합성은 수동 Ack 와 멱등성이 지킴).
이번에 워커가 경고를 받으면 **새 작업은 받지 않고 처리 중인 작업만 끝낸 뒤 쉬도록** 했다(drain).

## 구현

| 위치 | 내용 |
|---|---|
| `settlement-worker/.../SpotNoticeWatcher.java` | 1초마다 경고를 확인한다. 경고가 오면 RabbitMQ 소비를 멈추고(`container.stop()`), 처리 중인 1건(prefetch=1)이 커밋·Ack 될 때까지 최대 110초 기다린다. 지표 `swallow_worker_draining`, `swallow_worker_spot_notices` |
| 경고를 읽는 곳 (`SPOT_NOTICE_SOURCE`) | `file`: 로컬 실험. 주입기가 `docker exec ... touch /tmp/spot-notice` 로 경고를 보낸다. `imds`: EC2 메타데이터(IMDSv2) `spot/instance-action`. **EC2 에서는 아직 시험하지 않았다.** `none`: 끔 |
| `controller/fleet.py` `notify()`, `controller/injector.py` | 제어기의 회수 주입기가 경고 시각에 워커에게도 경고를 보낸다 |
| `SettlementWorker` | 다시 받은 작업을 `REDELIVERED <작업 ID>` 로그로 남긴다 (실험에서 다시 계산한 양을 센다) |
| `scripts/notice_drill.py` | 아래 비교 실험 |

부팅 중(Java 시작 전)에 온 경고도 놓치지 않도록, 경고 파일은 지우지 않고 시작하자마자 확인한다.
시험 실행에서 처음에는 시작할 때 파일을 지웠더니, 막 뜬 교체 서버가 경고를 놓치고 작업을 받았다가 죽는 경우가 있어 고쳤다.

경고는 최적화일 뿐이다. 경고가 오지 않거나 늦는 경우가 있으므로 정합성은 여전히 수동 Ack 와 멱등성이 지킨다.

## 실험

세 방식을 **같은 회수 일정**(경고 시각, 회수 6회, 20초 간격, 교체 서버 복구 시간 15초)으로 돌렸다.

- **none**: 경고 없음. 정해진 시각에 바로 kill. 교체는 kill 뒤 요청.
- **drain**: 경고를 받으면 마무리하고 쉰다. 교체는 kill 뒤 요청.
- **drain+replace**: 마무리하고, 교체 서버도 경고를 받는 즉시 요청 (AWS 재조정과 같은 동작).

경고는 kill 30초 전에 온다(실제는 120초. 실험 시간을 줄이려고 작업 길이보다 길게만 잡았다).
로컬 Docker, 워커 4대, 각 조합 3회. 작업은 짧은 작업(약 2초, 200건)과 긴 작업(약 15초, 60건) 두 가지.

### 결과 (3회 평균, 원자료 `docs/data/notice-drill-2026-11-25.csv`)

| 작업 | 방식 | 다시 계산한 작업 | p50 완료 시간 | p95 | 최대 | 전체 처리 시간 | 정합성 |
|---|---|---|---|---|---|---|---|
| 짧은 작업 (2초) | none | 4.0건 | 50.1초 | 108.6초 | 115.1초 | 141.5초 | 3/3 OK |
| | drain | 0건 | 76.1초 | 159.2초 | 164.0초 | 166.0초 | 3/3 OK |
| | drain+replace | 0건 | 57.0초 | 112.1초 | 118.6초 | 140.6초 | 3/3 OK |
| 긴 작업 (15초) | none | 6.0건 | 168.3초 | 264.4초 | 273.4초 | 274.5초 | 3/3 OK |

유실, 금액 불일치, 흡수한 중복은 18번 모두 0이었다.

### 해석

1. **마무리만 하면(drain) 오히려 느려진다.** 다시 계산하는 작업은 없어지지만, 경고를 받은 워커가 회수될 때까지 쉬는 동안
   그만큼 처리 능력이 빠진다. 교체는 회수 뒤에야 요청하므로, 경고가 없을 때보다 빈 시간이 길어진다(짧은 작업 p95 +47%).
2. **마무리와 조기 교체를 함께 해야 이득이다.** 긴 작업에서 drain+replace 는 다시 계산한 작업 0건, p95 −12.5%,
   전체 처리 시간 −12%였다(none 대비).
3. **작업이 짧으면 이득이 거의 없다.** 짧은 작업에서 drain+replace 는 none 과 거의 같았다(p95 +3%). 다시 계산하는 양이 2초짜리
   4건뿐이라 아낄 것이 적다. 시뮬레이터 ablation 에서 "재처리 부하" 항목의 효과가 0%였던 것과 같은 결과다.
   즉 **경고 처리의 가치는 작업 길이에 비례**한다. 수십 분짜리 변환·추론 작업에서 가장 크다.
4. **마무리가 경고 시간 안에 끝나야 한다.** 긴 작업 drain 3회 중 2회에서 6번 중 1번은 마무리가 30초 안에 끝나지 않아
   (마무리에 최대 25.9초, 작업 길이가 거래 수에 따라 다르다) 그대로 회수됐고, 그 작업은 다시 계산됐다(정합성은 그대로).
   실제 경고는 120초이므로 작업이 2분보다 짧으면 문제없고, 더 긴 작업은 중간 저장(체크포인트)이 필요하다.

### 남은 개선

- drain+replace 에서도 짧은 작업은 약간 느려졌다. 경고 즉시 소비를 멈추지 말고, "남은 시간 > 작업 길이"인 동안은 계속 받다가
  마지막에 멈추면 빈 시간을 더 줄일 수 있다.
- IMDS 경로는 EC2 에서 시험하지 않았다.

## 기존 동작 확인

경고 기능을 켠 상태(`SPOT_NOTICE_SOURCE=file`, 경고는 보내지 않음)로 장애 주입 매트릭스 8종을 다시 돌렸다. 8/8 PASS
(원자료 `docs/data/fault-matrix-2026-11-25-notice.csv`). 발행기 1% 종료 행은 이번에 흡수한 중복 254건, 최대 완료 시간 244초로
이전(98~189건, 116초)보다 컸다. 이 행은 발행기가 확률로 죽는 횟수에 따라 크게 흔들리고, 이번 변경은 발행기(API)를 건드리지 않았다.
목표 시간(300초) 안이다.
