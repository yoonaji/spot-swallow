# 복구가 느린 환경에서 실제 시스템으로 정책 비교 (2026-11-25)

시뮬레이터는 "복구 시간이 7.5분 이상이면 제안 기법이 목표 시간을 훨씬 잘 지킨다"고 했다. 이 결론이 시뮬레이터 안에서만
나오는지, 실제 제어기와 실제 워커에서도 나오는지 확인했다.

## 설정

| 항목 | 값 |
|---|---|
| 시스템 | 로컬 Docker (API, PostgreSQL, RabbitMQ, 워커 컨테이너), 제어기 `controller.main` |
| 느린 복구 흉내 | 새 워커를 띄울 때 부팅 지연(로그정규, 중앙값 600초, σ 0.42)을 넣는다. GPU 서버에 큰 모델을 올리는 상황을 흉내 낸 것이다. 실제 GPU 는 쓰지 않았다 |
| 회수 | 시뮬레이터와 같은 회수 기록(us-west-2c GPU 4대, Can't Be Late 공개 기록)을 **실제 속도로** 재생. 321.70h 부터 재생하면 8분 뒤 4대 중 3대, 이어서 나머지가 회수되고 한동안 스팟을 새로 만들 수 없다 |
| 워밍업 | 회수 주입은 15분 뒤에 시작한다. 그동안 정책마다 원하는 대수를 갖춘다 |
| 부하 | 초당 1.8건(포아송), 작업당 약 2초, 목표 시간 5분 |
| 측정 | 회수 주입이 시작된 뒤 접수된 작업만 센다. 비용은 제어기 로그의 스팟·온디맨드 워커-분 × 가정 가격(스팟 $0.037/h, 온디맨드 $0.107/h) |
| 실행 | `python3 scripts/live_compare.py --seeds 0 --policies <정책>` (정책당 약 55분, 1회씩) |

## 해석

- **시뮬레이터와 같은 방향의 결론이 실제 시스템에서도 나왔다.** 복구가 10분 걸리는 환경에서 대량 회수가 오면, AWS 재조정과 고정 여유는
  회수 뒤 접수된 작업의 40~50%가 목표 시간을 넘겼고, 제안 기법은 0%였다. 대신 비용은 AWS 재조정보다 19%, 고정 +2대보다 27% 많았다.
  (시뮬레이터, 복구 10분: 위반 7.46% · 1.75%, 비용 0.48 · 0.69)
- **차이의 원인은 회수가 오기 전에 이미 온디맨드를 섞어 둔 것이다.** 제안 기법은 회수 기록에서 "한꺼번에 다 회수되는 일이 잦다"(동시 회수
  비율 상위값 1.0)를 보고 처음부터 온디맨드 4~5대를 섞었다. 회수가 와도 온디맨드는 살아 있어 처리를 이어 갔다. 다른 정책은 회수 뒤에야
  새 서버를 요청했고, 그 서버가 준비되는 10분 동안 적체가 쌓였다(AWS 재조정 최대 996건).
- 위반율 숫자 자체는 시뮬레이터보다 훨씬 크다. 시뮬레이터는 12시간 구간 평균이고, 이 실험은 대량 회수 직후 약 20분만 측정했기 때문이다.

## 발견한 문제

- **전환할 때 기존 서버를 먼저 내렸다.** 제안 기법은 첫 제어 주기에 "스팟 1대 + 온디맨드 3대"를 목표로 정하고, 준비된 스팟 3대를 바로
  내린 뒤 온디맨드 3대를 새로 요청했다. 온디맨드가 준비되는 10분 동안 워커가 1대뿐이라 워밍업 중에 적체가 714건까지 쌓였다(측정 구간
  전이라 결과 표에는 들어가지 않았다). 새 서버가 준비된 뒤에 기존 서버를 내리도록(make-before-break) 고쳐야 한다.

## 한계

- 정책마다 1회씩만 돌렸다(회수 기록의 한 구간, seed 0). 같은 구간을 다른 seed 로 반복하거나 다른 회수 구간을 써서 확인해야 한다.
- 실제 GPU 와 실제 EC2 가 아니다. 부팅 지연은 흉내 낸 값이다.
- 처음 실행은 회수 기록을 10배속으로 재생했는데, 이러면 부팅 10분이 기록 기준으로 100분이 되어 조건이 맞지 않아 버렸다
  (`--speedup 1` 로 바꿈).
